## §0 测试口径

**被测环境（launch args 实测，取自运行中容器的 `server_args`）**

- 引擎：SGLang（fork）· 4× DGX Spark GB10 / sm_121a · switchless RoCE ring · **TP4 / EP2**
- 投机解码：`--speculative-algorithm DSPARK`，`--speculative-dspark-block-size 5`，
  `speculative_num_draft_tokens=6`（即 **draft k=5 / verify=6**）
- 上下文与容量：`--context-length 600000` · `--max-total-tokens 9600000` ·
  `--max-running-requests 16` · `--cuda-graph-max-bs-decode 16` · `--mem-fraction-static 0.90`
- 注意力 / MoE 后端：`--attention-backend dsv4` · `--moe-runner-backend flashinfer_mxfp4` ·
  `--fp8-gemm-backend flashinfer_cutlass` · `--chunked-prefill-size 4096`
- KV：`kv_cache_dtype=fp8_e4m3`（引擎日志实报）；`SGLANG_DSV4_KV_LAYOUT=fork-v4-fp4`
- 质量/解析：`--reasoning-parser deepseek-v41` · `--tool-call-parser deepseekv41` ·
  `--enable-decoder-swa-bounded-replay` · `grammar_backend=xgrammar`
- **fp4-indexer 已开**（`--enable-deepseek-v4-fp4-indexer`，`server_args.enable_deepseek_v4_fp4_indexer=True`）
- 服务面：引擎 loopback `127.0.0.1:8899`；对外经并发代理 `:8001`
- 镜像：`dsv41-sglang-optimized:v7` · SGLang `0.0.0.dev1+gda64c5cbb` · driver 580.173.02 / CUDA 13.0
  （完整身份见仓库根 `BUILD-IDENTITY.md`）

**计分口径**（对齐 LuZ0.4.5 板书 `FINAL-METRICS-2026-09-02`）

- uuid 冷前缀、每请求 p50 中位、`prefill = prompt_tokens / TTFT`、
  `decode = (ct−1) / (wall − TTFT)`、`agg = 每请求中位 × N`
- DE：512 输入 + 4096 输出（`ignore_eos`）；PR：512 / 2048 / 8192 / 32768 / 131072 / 524288 输入 × C1/2/4/8/16
- "Total decode"（common window）= 同一共享墙钟区间内所有流实际交付 token 之和（含调度停顿与投机突发）
- **单位口径铁律**：本栈内部 "GB" ≡ 1024³。凡跨单位运算只报**纯字节比**，
  避免单一口径倍数被下游照抄传播

decode 已按 `(ct−1)/(wall−ttft)` 归一，速率口径不受 ct 波动影响。

**schema 约束的代价**：结构化 prefill 显著低于自由文本（同为 512 输入，coding C1 551.2 vs 1450.8）
——每 token 都要过一次 grammar mask。高并发下代价被 decode 摊薄，两者收敛。

### 结构化通道两个坑（工程记录）

1. 🔴 `sampling_params.json_schema` 传 **dict 会打崩引擎**（xgrammar `TypeError: unhashable type: 'dict'`
   → scheduler 死 → 容器 247）。**必须传 JSON 字符串**。当前生产入口（:8001 网关透传）任何用户
   传 dict 形态 `response_format` 都可能触发全栈重启——**上游未修，属已知风险**。
2. 🟠 grammar 约束下 `ignore_eos=True` **失效**：schema 可终止时 EOS 照常 stop。
   要吃满预算，schema 必须带 `minItems` 等不可提前满足的约束。

## §5 结构化 vs 自由文本（按原始归档重算）

Rev.1.0 的对照表引用了自由基线值 62.3 / 222.6 / 356.1，这些值**无法在任何原始文件中溯到**
（见 §10 勘误）。下表按可溯源的 `data/de-freeform-20260917/` 重算：

| 对照格 | 自由文本 | 结构化 | 差值 |
|---|---:|---:|---:|
| coding C1 decode | 99.40 | 89.46 | **−10.0%** |
| coding C8 agg | 213.52 | 210.36 | −1.5% |
| coding C16 agg | 339.02 | 367.24 | **+8.3%** |
| json C16 agg | 336.90 | 269.79 | **−19.9%** |

**结论（与 Rev.1.0 相反，但都有数据支撑）**：结构化约束**在单流 / 低并发下明显更慢**
（C1 coding −10.0%），中并发持平（C8 −1.5%），高并发下 coding 反超 +8.3% 而 json 落后 −19.9%。
Rev.1.0 的"coding C1 +43.7% 反超"是拿一个不存在的基线算出来的，**该结论作废**。

> 关键工程结论不变：**引擎侧无回退**——schema 约束下 agg 吞吐与自由文本同量级
> （C16 coding 367 vs 339），xgrammar mask 未成为瓶颈。差异主要来自 grammar 的
> prefill 期 mask 开销与 token 形态效应。

## §9 网关链路（:8001）性能注记（2026-09-18）

`concurrency-proxy-v2`（:8001 → `127.0.0.1:8899`）与直连 8899 对比，1024-token 生成：

| 形态 | 修复前 | 修复后 | 备注 |
|---|---|---|---|
| 流式 | −15.7%（网关反而更快） | −11.4% | heartbeat 与 chunked 泵送效应 |
| 非流式 | **+156.4%** | **+4.7%** | `relay_plain` 原为整包 `await up.read()` 缓冲 |

**修复**：`relay_plain` 由整包缓冲改为分块流式泵送（`StreamResponse`），
非流式劣化 **+156.4% → +4.7%**（门槛 ≤+15%），流式无回归。
现场事实：live `UPSTREAM=127.0.0.1:8899`、`MAX_CONCURRENCY=16`。

**结论（已更新）**：网关不再是长输出的瓶颈（非流式 +4.7%），
但**长输出压测仍建议走流式**以获得最低墙钟。

> ⚠️ Rev.1.0 的 §8 记录的是修复**前**的数字（+156.4%）与"非流式大响应不建议经 8001"的结论，
> 该结论已被同日的 `relay_plain` 流式化推翻。两者都保留在此以便追溯。
